# PPA Pipeline

Daily sales-data pipeline: **Postgres → Sling → DuckDB → dbt → Dagster**.
Ingests 9 source tables every morning, gates dbt builds on a schema-drift check,
and produces staging + marts models for analytics.

## Features

- **Daily ingest ** — Sling replicates `public.*` from Postgres
  into DuckDB `raw.*` (incremental on `updated_at`/`created_at`, full-refresh for
  small dimensions). Job: `ppa_daily`.
- **Schema-drift gate** — `schema_drift` asset fails the run if Postgres columns
  drift from the DuckDB raw tables, before dbt builds. dbt only runs after a
  successful ingest via the `gate_dbt_on_ingest` sensor.
- **dbt staging + marts** — 9 `stg_*` views standardizing names/types, 9 marts
  tables (`dim_customers`, `dim_products`, `dim_categories`, `dim_devices`,
  `dim_payment_methods`, `fct_sales`, `fct_sale_revisions`,
  `fct_sale_revision_items`, `fct_payments`).
- **Telegram alerts** — success/failure run sensors via the Telegram Bot API
  (stdlib only, no extra deps). Enable them under Dagster UI → Automation → Sensors.

## Prerequisites

- Python 3.10–3.14, [`uv`](https://docs.astral.sh/uv/) (or pip + venv)
- Network access to the source Postgres

## Setup

1. **Env vars** — copy the template and fill in values (see table below):

   ```bash
   cp ppa_dagster/.env.local ppa_dagster/.env
   ```

2. **Install + run Dagster:**

   ```bash
   uv sync
   source .venv/bin/activate   # Windows: .venv\Scripts\activate
   dg dev                       # UI at http://localhost:3000
   ```

   (pip alternative: `python3 -m venv .venv && pip install -e ".[dev]"`, run from `ppa_dagster/`.)

3. **dbt** — from `ppa_dbt/`, with `DBT_TARGET`, `DUCKDB_DEV_DATABASE`,
   (`DUCKDB_PROD_DATABASE` for prod) set:

   ```bash
   dbt run
   dbt test
   ```

## Usage

- **Daily pipeline** — runs on schedule (04:00 Asia/Jakarta, job `ppa_daily`);
  trigger it manually from Dagster UI → Jobs → `ppa_daily` → Materialize.
- **dbt only** — from `ppa_dbt/`: `dbt run` then `dbt test`.
- **Sensors** — turn on `gate_dbt_on_ingest` and the Telegram sensors under
  Dagster UI → Automation → Sensors.


## Env vars

| Var | Used by | Purpose |
|---|---|---|
| `DBT_PROD_HOST` | Sling, schema check | Source Postgres host |
| `DB_SLING_USER` / `DB_SLING_PASSWORD` | Sling, schema check | Source Postgres credentials |
| `DUCKDB_DEV_DATABASE` | Sling target, schema check, dbt dev | Absolute path of the dev DuckDB file |
| `DUCKDB_PROD_DATABASE` | dbt prod | Path of the prod DuckDB file |
| `DBT_TARGET` | dbt | `dev` or `prod` |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | Telegram sensors | Optional; sensors only error if they fire |

## Notes

- `sale_revision_items` is ingested via custom SQL joining `sale_revisions`
  (3-day overlap window on `revision_created_at`) — see `replication.yaml`.
- Sling adds `_sling_loaded_at`; the drift check ignores it (plus
  `revision_created_at` on `sale_revision_items`).


Data is generated by self-developed POS App, currently used by real client. 

## Seed data (`ppa-anon.db`)
